## [unreleased]

### Added

#### File uploads
- Multipart file upload support in `Rest` (`src/Rest.ts`). `post()`, `patch()`, and `put()` take an optional fourth `files: FileAttachment[]` argument; when it is non-empty the request body becomes a `FormData` carrying the JSON payload under `payload_json` plus one `files[n]` part per attachment, and the `Content-Type` header is omitted so `fetch` can set it with the multipart boundary. Files deliberately travel as a separate argument rather than inside the payload, so the JSON body stays exactly what goes on the wire. Everything else — the per-bucket request queue, rate limit accounting, `429` handling, and `5xx` backoff — is shared with JSON requests rather than duplicated for uploads; the only upload-specific behaviour is that the `FormData` is rebuilt on each attempt, since a body already handed to `fetch` is consumed and cannot be replayed on a retry. Lists are validated before the request is sent: at most 10 files, no empty names, and no duplicate names (a duplicate would make an `attachment://<name>` reference ambiguous)
- `MessagePayload.attachments` (`src/Types/Internal.ts`) — `{ name, data, description? }[]`, where `data` is a `Buffer`, `Uint8Array`, or `string`. A `string` is uploaded as its UTF-8 bytes and is never read from disk, so there is no ambiguity between file contents and a path. `MessagePayload.flags` was added alongside it, which is what `IS_COMPONENTS_V2` will need. `InteractionCallbackMessages.attachments` (`src/Types/Interactions.ts`) takes the same shape, replacing the upload-less `Pick<Attachment, "id"> & Partial<...>` it previously declared
- `RetainedAttachment` (`src/Types/Internal.ts`) — `{ id, filename?, description? }`, naming an attachment already on a message so an edit keeps it. Editing replaces a message's whole attachment list, so anything left out is removed; an `attachments` entry is an upload when it carries `data` and a retained attachment otherwise, which means both can be mixed in one list
- `SplitAttachments()` (`src/Structures/Message.ts`) — splits a payload into the JSON body and the files to upload, turning each attachment into an `{ id, filename?, description? }` descriptor. That descriptor is what an `attachment://<filename>` reference in an embed or a `FileComponent` / `MediaGallery` resolves against, so the two halves are built together. Uploads are numbered by their position among the *files* rather than among the attachments, so interleaving them with retained attachments still lines each descriptor up with its `files[n]` part; retained entries keep their real ids, which are snowflakes and so never collide with those indices. It returns a shallow copy rather than mutating the caller's payload
- Attachments are wired into `channel.send()`, `message.reply()`, `message.update()`, `user.send()`, `webhook.send()`, and the interaction responses — `reply()`, `editReply()`, `followUp()`, and `update()`. The two callback-route responses (`reply()` and `update()`) nest the message body in `data` while the uploads stay top-level form parts, which is the shape Discord expects. `CreateMessagePayload()` now accepts an attachment-only message rather than rejecting it as empty
- Multipart test coverage (`src/Tests/Multipart.test.ts`), asserting the form body and its parts, the absent `Content-Type`, that file-less requests still send JSON, and that a retried request builds a fresh body

#### Emoji and sticker uploads
- `guild.emojis.create({ name, image, roles? })` (`src/Managers/Emojis.ts`) — uploads a custom emoji and caches the result. `image` takes the raw bytes of the file (`UploadInput`) rather than a `FileAttachment`: this endpoint already takes the emoji's name as its own argument and Discord ignores a filename here, so there is nothing left worth naming. An already-encoded data URI is still accepted, so callers that encoded their own image keep working. `roles` accepts role IDs or `Role` objects interchangeably
- `guild.stickers.create({ name, description, tags, file })` (`src/Managers/Stickers.ts`) — uploads a guild sticker. `file` is the bytes of a PNG, APNG, GIF, or Lottie JSON file; a Lottie animation may also be handed over as the object itself, which is serialized for you, since it is the one sticker format that is plausibly built in code rather than read off disk. `tags` takes a string or a list, which is comma-joined. The format is checked against what Discord accepts before a request is spent on it — APNG is not treated separately because it is a PNG with an extra chunk, so it detects as `image/png` and Discord picks the animation up from the file itself
- `DetectMimeType()`, `ResolveUpload()`, and `ToDataURI()` (`src/Utils.ts`) — the shared upload plumbing. `DetectMimeType()` reads the type from the file's magic bytes and never from a filename: this library never touches the disk, so uploads arrive as bytes the caller read themselves and often have no filename at all, and where there is one an extension is only a claim that a `.png` full of JPEG data would have Discord reject. `ToDataURI()` builds the base64 data URI Discord's JSON image fields want, passing an already-encoded one straight through; `ResolveUpload()` supplies the filename a multipart form still structurally needs, built from the name of the thing being created plus the detected type's extension. `UploadInput` (`src/Types/Internal.ts`) names the `Buffer | Uint8Array` these take. An MP3 with no ID3 tag ahead of it has no signature to match, only a frame header, so that header's fixed fields are all checked rather than just its 11 sync bits - the sync bits alone also match a UTF-16LE byte order mark, which would have `FF FE ...` text detected as audio
- `MultipartMode` and `MultipartUpload` (`src/Rest.ts`) — `post()`, `patch()`, and `put()` now accept either a bare `FileAttachment[]` or a `{ files, multipart }` object as their fourth argument. The default `payload_json` layout is unchanged; the new `fields` layout sends every top-level key of the JSON body as its own form field and the single file as a part named `file`, which is what sticker creation requires and `payload_json` is rejected for. `null` and `undefined` fields are dropped rather than stringified into the literal text `"null"`, and `fields` requests carrying more than one file are rejected before they are sent, since every file would be appended under the same part name and overwrite the last
- Every image field Discord takes inline in a JSON body rather than as a multipart part now accepts raw file bytes and encodes them on the way out: `guild.modify()`'s `icon`, `splash`, `discoverySplash`, and `banner`; `guild.roles.create()` / `role.modify()`'s `icon`; a scheduled event's `image` on create and modify; a webhook's `avatar` on create and edit; and `guild.soundboardSounds.create()`'s `sound`, whose MP3 and OGG signatures `DetectMimeType()` now recognizes. `ImageInput` (`src/Types/Internal.ts`) names what they take — `Buffer | Uint8Array | string`, where a `string` must still be a data URI, since nothing here reads from disk, so callers that encoded their own image are unaffected
- `EncodeImage()` (`src/Utils.ts`) — the nullable form of `ToDataURI()` used at the edit sites. Discord's image fields distinguish three states and only one of them is a file, so absent leaves the image alone, `null` clears it, and both pass straight through
- Upload test coverage (`src/Tests/Multipart.test.ts`), covering the `fields` form layout and its single-file rule, magic-byte detection for each supported format, Lottie recognition by leading brace, data URI encoding and pass-through, and `StickerCache.create()`'s Lottie serialization and format rejection

#### Message fetching
- `MessageManager` (`src/Managers/Messages.ts`) on `channel.messages`, with an overloaded `fetch()`: `fetch(id)` reads a single message back by id, and `fetch({ limit?, before?, after?, around? })` pages a channel's history. Available on every channel using the `Messageable` mixin — `GuildTextChannel`, `GuildVoiceChannel`, and `GuildThreadChannel` — and created lazily on first access, so channels built during a `GUILD_CREATE` burst do not each allocate one. Messages could previously be sent, edited, deleted, pinned and reacted to, but never read back
- The manager holds **no cache**, unlike the guild collections. A channel's message history is unbounded, so caching it would mean owning an eviction policy and the memory cost of thousands of messages; every call goes straight to the API and returns fresh `Message` instances. Message authors and mentions still land in the global user cache, since `Message.patch()` upserts them. `send()`, `deleteMessage()`, and `bulkDeleteMessages()` stay on the channel itself rather than moving onto the manager
- `before`, `after`, and `around` are mutually exclusive — Discord rejects more than one — so the manager throws before the request is sent rather than letting it fail server-side. `limit` is deliberately not range-checked client-side, matching `GuildBanManager`

#### Member fetching
- `MemberCache.fetch()` (`src/Managers/Members.ts`) is now overloaded: `fetch(id)` reads a single member as before, and `fetch({ limit?, after? })` pages `GET /guilds/{id}/members`, upserting every returned member into the guild's member cache. Following `GuildBanManager` and `MessageManager` rather than adding a separately named bulk method keeps one shape for "single by id, or a page by options" across the library; `fetchAll()` stays reserved for the argument-less listings (threads, webhooks, integrations, soundboard sounds). Both list routes require the privileged `GuildMembers` intent
- `MemberCache.fetchAll()` — pages `fetch()` at Discord's 1,000-member maximum until a short page comes back, using the last id of each page as the next `after`. This is the rare whole-guild case: it costs one request per 1,000 members and is heavily rate limited, so a targeted `fetch(id)` or `search()` is preferable whenever the whole list is not actually needed
- `MemberCache.search(query, limit?)` — `GET /guilds/{id}/members/search`, matching a username or nickname prefix. This is the cheap answer to "find the member called X", which otherwise forces a full `fetchAll()` scan
- `MemberFetchOptions` (`src/Managers/Members.ts`) is exported alongside them, mirroring `MessageFetchOptions`
- Member fetching test coverage (`src/Tests/MemberCache.test.ts`), covering both overloads, query serialisation, in-place upsert of an already-cached member, `fetchAll()`'s paging and its single-call short-circuit, and `search()`

#### Gateway member requests
- `MemberCache.fetchGateway(options?)` (`src/Managers/Members.ts`) — fetches members over the gateway with `RequestGuildMembers` (op 8) instead of REST, resolving with every member once the last chunk of the response arrives. It is not rate limited per 1,000 members the way `fetchAll()` is, and it is the only way to fetch members together with their presences or to look up a batch of up to 100 user ids in one call. `GatewayMemberFetchOptions` (`query`, `limit`, `userIds`, `presences`, `time`) is exported alongside it
- Requests are validated before they are sent: `query` and `userIds` are mutually exclusive, `userIds` is capped at 100, and the required intents are checked against `client.socket.intents` with `HasIntent`. Discord silently drops a request whose intents are missing, so without the guard the call would hang until its timeout with no indication of why. This is `HasIntent`'s first internal use
- `WSClient.requestGuildMembers(data)` (`src/WSClient.ts`) — the raw op 8 send, and `RequestGuildMembersPayload` (`src/Types/DiscordGateway.ts`) models its body. Op 8 was defined in `GatewayOpCodes` from the start but had never been sent
- `GatewayEvents.GuildMembersChunk` (`GUILD_MEMBERS_CHUNK`) and its `MembersChunk` handler (`src/Events/Members.ts`), which caches every member in the chunk, caches any presences it carries (dropping `offline` ones, matching `PresenceUpdate`), and emits the chunk as `ClientEvents.GuildMembersChunk` with a `GuildMembersChunkPayload`. Listening to that event streams a large fetch instead of awaiting it
- Chunks are matched back to the request that asked for them by a nonce the manager generates and Discord echoes on every chunk. The pending state lives in a `Collector` (`src/Collector.ts`) filtered on that nonce rather than in a request map on `WSClient`, so concurrent requests do not cross-talk, a reconnect cannot leak a pending promise, and a response that never completes rejects on the collector's own `time` timeout (30s by default)
- Test coverage across `src/Tests/MemberCache.test.ts` (multi-chunk reassembly, nonce isolation and the timeout, the `userIds` variant, and each validation error), `src/Tests/GatewayEvents.test.ts` (chunk caching, the offline-presence rule, and the uncached-guild guard), and `src/Tests/WSClient.test.ts` (the op 8 frame on the wire)

#### Thread creation and listing
- `ThreadManager` (`src/Managers/Threads.ts`) on `channel.threads`, mixed in by the new `Threadable` mixin (`src/Mixins/Channels/Threadable.ts`) and so present on `GuildTextChannel`, `GuildAnnouncementChannel`, and `GuildForumChannel`. Created lazily through a module-level `WeakMap` for the same reason as `MessageManager` — a `#private` field would not survive `clone()`, which copies own properties onto a bare instance. Every thread *event* was already handled and cached, but no thread could be created or listed from the library
- `create()` — `POST /channels/{id}/threads` for a standalone thread, defaulting `type` to `PUBLIC_THREAD`. `createForumPost()` uses the same route for forum and media channels, where a post's first message travels in the request; it runs the message through `SplitAttachments()`, so a forum post can be opened with embeds and file uploads. `createFromMessage()` — `POST /channels/{id}/messages/{id}/threads` — starts a thread from an existing message, whose id becomes the thread's. All three take an audit log `reason`
- `fetchActive()` reads `GET /guilds/{id}/threads/active` and narrows the result to threads parented to this channel; Discord has no per-channel active listing, so the sibling channels' threads are cached rather than discarded. `fetchArchived()`, `fetchArchivedPrivate()`, and `fetchJoinedArchivedPrivate()` cover the three archived routes and return `{ threads, hasMore }`, where `before` is an archive timestamp for the first two and a thread id for the joined-private listing
- The manager holds no cache of its own — threads are channels, so everything it returns is upserted into `guild.channels`, and each listing's `members` array is seeded into the corresponding thread's `ThreadMemberCache`
- Thread manager test coverage (`src/Tests/ThreadManager.test.ts`), covering lazy manager reuse, each creation route's payload and audit log header, forum post nesting, the guild-wide active listing and its narrowing, archived pagination and `hasMore` defaulting, and member seeding

#### Webhooks
- `Webhook` structure (`src/Structures/Webhook.ts`) covering the full webhook object, with lazy `guild` / `channel` getters that resolve from cache, an `avatarURL()` helper that returns `null` when no avatar hash is set, and a `toString()` that prefers the `url` Discord sent over a reconstructed one. Actions are `edit()`, `delete()`, and `send()`; `edit()` and `delete()` use the token-authenticated route when the webhook carries a `token` and the permission-checked route otherwise, and `edit()` throws rather than silently failing when asked to move a tokenless-route-only `channel_id` over the token route. `send()` always requests `?wait=true` so it can return a real message, passes `thread_id` as a query parameter rather than in the body, and throws when the webhook has no token
- `WebhookCache` (`src/Managers/Webhooks.ts`) on `guild.webhooks`, with `fetch(id)`, `fetchAll()`, `fetchChannel(channelId)`, and `create(channelId, options, reason?)`. Discord never sends webhooks in `GUILD_CREATE` and `WEBHOOKS_UPDATE` names only the channel that changed, so the cache starts empty and `fetchChannel()` is the intended way to resync after that event
- `WebhookMessage` (`src/Structures/WebhookMessage.ts`) — what `webhook.send()` now returns, in place of a plain `Message`. The message a webhook sends is authored by the webhook rather than the bot, which made both of the inherited edit paths wrong: `Message.update()` refuses it outright on the author comparison, and `Message.delete()` goes through the channel route, which needs `MANAGE_MESSAGES`. `WebhookMessage` overrides the two to use `/webhooks/{id}/{token}/messages/{id}` instead, which needs no permissions at all, and carries the thread the message landed in so a later edit addresses the right channel. The genuinely channel-scoped inherited operations — `reply()`, `pin()`, `react()` — are left alone, since a webhook token cannot perform them. `update()` still runs the payload through `PreparePayload()` with the message's own flags, so a Components V2 message stays held to the v2 rules across an edit
- `webhook.fetchMessage(id, threadId?)`, `webhook.editMessage(id, content, threadId?)`, and `webhook.deleteMessage(id, threadId?)` (`src/Structures/Webhook.ts`) — the webhook message routes, for messages whose id is known without having the object that `send()` returned. `editMessage()` cannot hold the edit to the v2 rules on the strength of what it is editing, since the message is addressed by id rather than fetched and its flags are never seen — the same trade-off `interaction.editReply()` documents; `fetchMessage()` first when that matters. All three are token-only, as Discord offers no bot-authenticated equivalent, and throw on a tokenless webhook
- `channel.follow(targetChannelId, reason?)` on `GuildAnnouncementChannel` (`src/Structures/Channels/GuildAnnouncementChannel.ts`) — `POST /channels/{id}/followers`, relaying everything crossposted here into another channel. Returns the new `DiscordFollowedChannel` (`src/Types/DiscordAPITypes.ts`); the Channel Follower webhook Discord creates lives in the *target* channel's guild, so there is nothing sensible to upsert into this guild's `webhooks` cache and it is deliberately left alone

#### Components v2
- `ComponentBuilder` (`src/Builders/ComponentBuilder.ts`) — abstract base for component builders, carrying the optional `id` every component shares and a chainable `setId()` that rejects non-integers and values outside 32 bits. `id` is what lets a specific component be targeted when editing a message. `id` is not an alternative to `custom_id` — `custom_id` routes an interaction back to you, `id` addresses the component for editing and ordering. **Every** component builder now extends it: the v2 builders, `ActionRowBuilder` — whose `from()` also takes a full `ActionRow` as well as a bare components array, so a row inside a container keeps its `id` across a round-trip — the three button builders, all five selects through `BaseSelectBuilder`, and the two modal component builders (`TextInputBuilder`, `LabelBuilder`). Each carries `id` through its static `from()` and checks it from `validate()`. The buttons needed a type change first: `BaseButton` and `PremiumButton` were built on neither `BaseComponent` nor each other, so the button payload types carried `custom_id` but no `id` at all; both now derive from `BaseComponent`, which adds an optional `id` to `InteractiveButton`, `LinkButton`, and `PremiumButton`
- `TextDisplayBuilder` (`src/Builders/TextDisplayBuilder.ts`) — markdown text rendered like message content, respecting the message's `allowed_mentions`. Discord's 4,000-character limit applies across all of a message's text rather than per-component, so the builder validates only that `content` is non-empty rather than inventing a per-component cap
- `SeparatorBuilder` (`src/Builders/SeparatorBuilder.ts`) — vertical padding with an optional divider line. Both fields are optional and are left unset unless explicitly set, so Discord applies its own defaults (`divider` true, `spacing` `SMALL`); `setSpacing()` rejects anything that is not `SeparatorSpacingSizes.SMALL` or `.LARGE`, which only untyped JavaScript callers can produce
- `ThumbnailBuilder` (`src/Builders/ThumbnailBuilder.ts`) — a small image, valid only as a `Section` accessory. `media` plus optional `description` (alt text, max 1024) and `spoiler`. Discord accepts only images, gifs, and animated webp here, which the builder does not check: that is a property of the bytes behind the url rather than of the url itself, and an extension is only a claim
- `SectionBuilder` (`src/Builders/SectionBuilder.ts`) — 1-3 `TextDisplay`s with an accessory alongside them. The bounds and a missing accessory are `validate()` cases, but a child's *type* is rejected eagerly in the setters — `setAccessory()` for anything that is neither a button nor a thumbnail, and `addComponents()` / `setComponents()` for anything that is not a text display — since a wrong child type is a structural mistake rather than an unfinished one. A half-built text display is still accepted, matching `ContainerBuilder`. The eager check is what actually catches this, since the send path never calls a component's own `validate()`; without it a button in a section would reach Discord as a 400
- `MediaGalleryBuilder` (`src/Builders/MediaGalleryBuilder.ts`) — 1-10 images or videos in a grid, via `addItems()` / `setItems()`. Items are plain objects rather than components, so there is no item builder; a bare url string is accepted as shorthand for an item with no alt text
- `FileBuilder` (`src/Builders/FileBuilder.ts`) — an uploaded file rendered inline. Only `attachment://<filename>` references are valid, checked twice: `setFile()` rejects any other url, and the send path rejects a filename with no matching attachment. `name` and `size` are `readonly` with no setter — Discord populates them and ignores anything sent, so a setter would only look like it did something, though `from()` still carries them through a round-trip
- `ContainerBuilder` (`src/Builders/ContainerBuilder.ts`) — a bordered, optionally accented group holding any of the other components, with an optional nullable `accent_color` and `spoiler`. A nested container is rejected with its own error message rather than the generic wrong-type one, since it is the mistake most worth naming, and reports identically whether it was added directly or hydrated through `from()` — the mapping asserts before it runs, so a child it has no case for is never reduced to `undefined` first. `setAccentColor(null)` clears the color, which is distinct from leaving it unset
- `ResolveMedia()`, `ValidateMedia()`, and `ValidateMediaDescription()` (`src/Builders/UnfurledMedia.ts`) — shared by the three media-bearing builders, so every media setter takes a bare url string as shorthand for an `UnfurledMediaItem` and they all reject the same way
- `ResolveColor()` (`src/Utils.ts`) — now shared by `EmbedBuilder.setColor()` and `ContainerBuilder.setAccentColor()`, so both take `number | "#RRGGBB"` and reject identically. `EmbedBuilder.setColor()`'s behaviour is unchanged
- The Components v2 send path. `PreparePayload()` (`src/Structures/Message.ts`) wraps `SplitAttachments()` with `ResolveComponentsV2Flags()` (`src/Builders/ComponentsV2.ts`), and every send path now funnels through it — `channel.send()`, `message.reply()` / `.update()`, `user.send()`, `webhook.send()`, forum post creation, and the interaction responses. A message using v2 components is flagged with `IS_COMPONENTS_V2` automatically, so nothing has to be hand-written any more, and the flags are applied to the copied body rather than to the caller's payload
- Enforced on the way out: the v1 features a v2 message cannot also carry (`content`, `embeds`, `sticker_ids`, `poll`), the message-wide budgets (40 components counting nested children, 4,000 characters across every `TextDisplay`), and that each `attachment://` reference names a file actually being uploaded — a mismatched filename now throws locally, naming the component, instead of returning a 400 that names nothing. A single recursive pass (`SummarizeComponents()`) collects all of it. An `ActionRow` is deliberately not treated as a v2-only type, so an action-row-only payload stays a v1 message. The per-component `validate()` methods stay opt-in; the send path only enforces what a single component cannot see for itself
- Edits pass the edited message's flags to `PreparePayload()` — `message.update()` its own, and a component interaction's `update()` those of the message it is attached to — so a message that is already v2 stays held to the v2 rules even when the edit alone would not look like one. `Repliable.editReply()` cannot do the same: it addresses the original response by token and never sees its flags
- Components v2 test coverage across `src/Tests/ComponentsV2.test.ts` (every builder, its validation cases, and `from()` round-trips) and the new `src/Tests/ComponentsV2Payload.test.ts` (flagging, the mixing rejections, the limits, attachment resolution, and the edit-time flag inheritance), both kept separate from the v1 `src/Tests/Components.test.ts` so the v1 suite stays a stable regression surface
- Send-path coverage (`src/Tests/SendPaths.test.ts`) — a table over all twelve `PreparePayload()` call sites, asserting for each that a v2 payload arrives at REST flagged, that a v1/v2 mix is rejected *before* the request leaves, and that uploads are split out of the JSON body into the files argument. The rules were well covered, but only ever by calling `PreparePayload()` directly, so a send path that stopped calling it would have gone unnoticed — "every send path is unskippable" was the one claim nothing tested. Also pins the three paths that thread the edited message's flags through and the two that structurally cannot (`editReply()` and `webhook.editMessage()` address what they are editing by token or id, so its flags are never in hand), so changing either is a deliberate act. The assertions are behavioural rather than a spy on `PreparePayload()`: each call site holds a direct ESM import binding, which a module-export spy would not intercept

#### Inbound component fields
- The response-only fields of `UnfurledMediaItem` (`src/Types/Components.ts`) — `proxy_url`, `height`, `width`, `content_type`, `attachment_id`, and `loading_state`, with the `UnfurledMediaItemLoadingStates` constant and its `UnfurledMediaItemLoadingState` union. Discord populates these on a thumbnail, media gallery item, or file component it sends back; only `url` is ever sent, so all six are optional and reading one off a received component no longer needs a cast
- `values` on the select types (`BaseSelect`, `src/Types/Components.ts`) — the options a user chose, which Discord populates on the component itself when a *modal* is submitted. A message component's selections still arrive on `MessageComponentData.values`, since those come back as interaction data rather than as the component, so the two are not interchangeable

#### Gateway
- Gateway connection test coverage (`src/Tests/WSClient.test.ts`) for the paths a long-running client actually lives on: the out-of-cycle heartbeat op 1 asks for, both halves of the `INVALID_SESSION` branch (resumable keeps the session and sends `RESUME`, non-resumable drops it and re-identifies), a heartbeat the gateway never acknowledges reconnecting instead of sending into a dead connection, heartbeat and reconnect timers being cleared on close, `destroy()`, and a direct `initialize()`, and the session id and resume url coming off `READY` and being dropped by `destroy()`. The timer tests count timers rather than sockets - a reconnect that fires and is ignored by the destroyed guard is indistinguishable from a cancelled one otherwise
- `USER_UPDATE` dispatch handler (`src/Events/Users.ts`), surfaced as the `UserUpdate` client event, and the `GatewayEvents.UserUpdate` type it needed — the event was not modeled at all. No intent is required; Discord sends it for every user the bot shares a guild with. `oldUser` is a detached `clone()` taken before the cache is patched, matching every other `*Update` handler, so a username or avatar change can actually be diffed. The handler also reassigns `client.user` when the updated user is the bot's own, which is what previously left `client.user` stale for the lifetime of the process after an application edit
- `RESUMED` dispatch handler (`src/Events/Resumed.ts`), surfaced as the argument-less `Resumed` client event. `GatewayEvents.Resumed` was already modeled and `WSClient` already acted on the frame, but it short-circuited before `dispatch()`, so nothing above the socket could observe a successful resume. `WSEvents.Resumed` is unchanged and remains the socket-level signal; `ClientEvents.Resumed` is the public one. `Ready` is deliberately not re-emitted on a resume — the client was already ready, and the gateway replays what was missed rather than re-sending the session
- `TYPING_START` dispatch handler (`src/Events/Typing.ts`), surfaced as the `TypingStart` client event. Emits the resolved `guild`, `channel`, and `user` (each falling back to a bare `{ id }` object when uncached, with `guild` `null` for DMs), the guild-only `member` payload upserted into the guild's member cache (`null` in DMs), and `timestamp` converted from Discord's unix-seconds value to a `Date`
- `AUTO_MODERATION_RULE_CREATE`, `AUTO_MODERATION_RULE_UPDATE`, and `AUTO_MODERATION_RULE_DELETE` dispatch handlers (`src/Events/AutoModeration.ts`), surfaced as the `AutoModerationRuleCreate` / `AutoModerationRuleUpdate` / `AutoModerationRuleDelete` client events. Requires the `AutoModerationConfiguration` intent. Rules are wrapped in the new `AutoModerationRule` structure (`src/Structures/AutoModerationRule.ts`) and cached per guild on `guild.autoModerationRules` (`src/Managers/AutoModeration.ts`). Discord never includes rules in `GUILD_CREATE`, so that cache starts empty and fills from gateway events or an explicit `fetch(id)` / `fetchAll()`; `AutoModerationRuleDelete` therefore emits the raw payload whenever the rule was not already cached
- `AUTO_MODERATION_ACTION_EXECUTION` dispatch handler (`src/Events/AutoModeration.ts`), surfaced as the `AutoModerationActionExecution` client event with a camelCased `AutoModerationActionExecutionPayload`. Requires the `AutoModerationExecution` intent. Nothing is cached — the event reports an occurrence, not an entity — and the optional `channelId` / `messageId` / `alertSystemMessageId` fields are omitted rather than nulled when Discord leaves them out
- `MESSAGE_REACTION_REMOVE_ALL` and `MESSAGE_REACTION_REMOVE_EMOJI` dispatch handlers (`src/Events/Reactions.ts`), surfaced as the `ReactionRemoveAll` / `ReactionRemoveEmoji` client events, completing the reaction family. Both emit the resolved `guild` and `channel` (falling back to a bare `{ id }` object when uncached, with `guild` `null` for DMs) alongside `messageId`, and `ReactionRemoveEmoji` adds the cleared `emoji`. Discord sends no information about which reactions were removed, and the library has no message cache, so neither handler mutates any cache state
- `MESSAGE_POLL_VOTE_ADD` and `MESSAGE_POLL_VOTE_REMOVE` dispatch handlers (`src/Events/Polls.ts`), surfaced as the `MessagePollVoteAdd` / `MessagePollVoteRemove` client events. Requires the `GuildMessagePolls` intent in guilds, or `DirectMessagePolls` in DMs. Both emit the resolved `guild`, `channel`, and `user` (each falling back to a bare `{ id }` object when uncached, with `guild` `null` for DMs) alongside `messageId` and `answerId`, which matches the chosen answer's `answer_id` in the poll's `answers` array. Nothing is cached: the payload carries no message and the library has no message cache, so a running tally has to be kept by the listener or re-read with a message fetch. Changing a vote in a single-select poll arrives as a remove followed by an add, so the two events are not independent
- `GUILD_SCHEDULED_EVENT_CREATE`, `GUILD_SCHEDULED_EVENT_UPDATE`, and `GUILD_SCHEDULED_EVENT_DELETE` dispatch handlers (`src/Events/GuildScheduledEvents.ts`), surfaced as the `GuildScheduledEventCreate` / `GuildScheduledEventUpdate` / `GuildScheduledEventDelete` client events. Requires the `GuildScheduledEvents` intent. Events are wrapped in the new `GuildScheduledEvent` structure (`src/Structures/GuildScheduledEvent.ts`, with `modify()` and `delete()`) and cached per guild on `guild.scheduledEvents` (`src/Managers/GuildScheduledEvents.ts`, with `fetch(id)` / `fetchAll()` / `create()`). Discord includes `guild_scheduled_events` in `GUILD_CREATE`, so the cache is seeded on connect rather than starting empty. Starting, ending, and cancelling an event all arrive as `GuildScheduledEventUpdate` `status` changes.
- `GUILD_SCHEDULED_EVENT_USER_ADD` and `GUILD_SCHEDULED_EVENT_USER_REMOVE` dispatch handlers (`src/Events/GuildScheduledEvents.ts`), surfaced as the `GuildScheduledEventUserAdd` / `GuildScheduledEventUserRemove` client events, completing the scheduled event family. Requires the `GuildScheduledEvents` intent. Both emit the `event`, the `user`, and the `guild`; the payload carries ids only, so `event` and `user` each fall back to a bare `{ id }` object when uncached. No subscriber cache was added — Discord never sends a subscriber list over the gateway, so any such cache would be permanently partial — but `event.userCount` is incremented/decremented (floored at zero) when it is already known from a `fetch` that requested user counts, and left `undefined` otherwise rather than being invented from a zero baseline
- `CHANNEL_PINS_UPDATE` dispatch handler (`src/Events/Channels.ts`), surfaced as the `ChannelPinsUpdate` client event. Emits the resolved `guild` and `channel` (falling back to a bare `{ id }` object when uncached, with `guild` `null` for DMs) alongside `lastPinTimestamp`, normalized to `null` when Discord omits it. Discord does not say which message was pinned, and does not fire this event when a pinned message is deleted, so nothing is cached
- `PRESENCE_UPDATE` dispatch handler (`src/Events/Presence.ts`), surfaced as the `PresenceUpdate` client event. Requires the **privileged** `GuildPresences` intent. Presences are wrapped in the new `Presence` structure (`src/Structures/Presence.ts`, with `customStatus`, `activityOfType()`, `isOn(device)`, and `user` / `member` accessors) and cached per guild on `guild.presences` (`src/Managers/Presences.ts`), with `member.presence` as a shorthand. Discord includes `presences` in `GUILD_CREATE`, so the cache is seeded on connect. Offline users are never retained — Discord omits them from `GUILD_CREATE` and the handler drops an entry once its status goes `offline` — so `member.presence` is `undefined` for anyone offline, unseen, or when the intent is off. `oldPresence` is a detached `clone()` taken before the cache is patched, so it can actually be diffed against `newPresence` — the treatment since generalized to every `*Update` handler. The payload's `user` object is partial (Discord guarantees only `id`), so it is only upserted into the user cache when it arrives complete, never blanking an already-cached user
- Inbound presence types (`src/Types/DiscordAPITypes.ts`) — `DiscordPresence`, `DiscordActivity` and its `Timestamps` / `Emoji` / `Party` / `Assets` / `Secrets` sub-shapes, `DiscordClientStatus`, `DiscordPartialUser`, and the `ActivityFlags` bitfield. `ClientActivity` is now derived from `DiscordActivity` via `Pick` so the outbound and inbound shapes cannot drift apart, and `PresenceStatus` adds the outbound-only `invisible` that `Client.setStatus()` accepts (inbound presences never report it — Discord shows invisible users as `offline`, so `Status` deliberately omits it)
- `DiscordGuildCreate` type (`src/Types/DiscordAPITypes.ts`) — names the `DiscordGuild` + `channels` / `members` / `guild_scheduled_events` / `presences` intersection that `GUILD_CREATE` actually delivers, replacing the copy of it that was inlined in both `Guild`'s constructor and `patch`
- `guild.channels` is now seeded with the guild's active threads on connect. `GUILD_CREATE` carries a `threads` array — every active thread the bot can see — which `DiscordGuildCreate` did not model and `Guild.patch()` did not read, so threads were missing until a `THREAD_CREATE` / `THREAD_LIST_SYNC` arrived or `channel.threads.fetchActive()` was called. They are upserted after `channels` so a thread's parent is already cached, and carry the same `guild_id` fallback `ThreadListSync` uses since Discord omits it on nested threads. Each thread's `member` blob seeds `thread.members` for the current user at the same time, via the existing `GuildThreadChannel.patch()`
- `WEBHOOKS_UPDATE` dispatch handler (`src/Events/Webhooks.ts`), surfaced as the `WebhooksUpdate` client event. Requires the `GuildWebhooks` intent. Emits the resolved `guild` and `channel` (falling back to a bare `{ id }` object when uncached; the event is guild-only, so `guild` is never `null`). Discord sends no information about which webhook changed or how, only where it happened, so nothing is cached — fetch the channel's webhooks to see the new state
- `THREAD_CREATE`, `THREAD_UPDATE`, and `THREAD_DELETE` dispatch handlers (`src/Events/Threads.ts`), surfaced as the `ThreadCreate` / `ThreadUpdate` / `ThreadDelete` client events. Threads are cached alongside regular channels in the guild's `ChannelCache`, so `guild.channels` is the single source of truth and `BaseChannel.isThreadChannel()` narrows to `GuildThreadChannel`. `ThreadDelete` emits the cached thread when it has one and the raw partial payload otherwise
- `THREAD_MEMBER_UPDATE`, `THREAD_MEMBERS_UPDATE`, and `THREAD_LIST_SYNC` dispatch handlers (`src/Events/Threads.ts`), surfaced as the `ThreadMemberUpdate` / `ThreadMembersUpdate` / `ThreadListSync` client events, completing the thread family. Thread membership is wrapped in the new `ThreadMember` structure (`src/Structures/ThreadMember.ts`) and cached per thread on `thread.members` (`src/Managers/ThreadMembers.ts`, with `fetch(userId)` / `fetchAll()`), keyed by user id. `ThreadMemberUpdate` only ever fires for the current user; `ThreadMembersUpdate` is a delta (`added` / `removed`) that Discord caps at 50 additions and only populates beyond the current user with the **privileged** `GuildMembers` intent, so use `thread.members.fetchAll()` when the complete list matters. `ThreadListSync` is a true sync: it caches every thread it carries, then evicts cached threads under the synced `channel_ids` (or the whole guild, when Discord omits that field) that the payload did not list, reporting their ids as `evicted` since they are already gone from the cache by the time listeners run
- `INTEGRATION_CREATE`, `INTEGRATION_UPDATE`, and `INTEGRATION_DELETE` dispatch handlers (`src/Events/Integrations.ts`), surfaced as the `IntegrationCreate` / `IntegrationUpdate` / `IntegrationDelete` client events. Requires the `GuildIntegrations` intent. Integrations are wrapped in the new `Integration` structure (`src/Structures/Integration.ts`, with a `role` accessor and `delete()` — Discord deprecated the modify endpoint, so there is deliberately no `modify()`) and cached per guild on `guild.integrations` (`src/Managers/Integrations.ts`, with `fetch(id)` / `fetchAll()`). Discord never includes integrations in `GUILD_CREATE`, so that cache starts empty and fills from gateway events or an explicit fetch; `fetch(id)` has to list every integration and pick from the result because there is no single-integration endpoint. `INTEGRATION_DELETE` carries ids only, so `IntegrationDelete` emits a bare `{ id }` object when the integration was not cached, alongside the `guild` and the `applicationId` Discord sends for `discord` type integrations. Everything past `account` is absent for bot and `guild_subscription` integrations, so the subscriber fields stay `undefined` rather than being defaulted
- `GUILD_INTEGRATIONS_UPDATE` dispatch handler (`src/Events/Integrations.ts`), surfaced as the `GuildIntegrationsUpdate` client event, completing the integration family. Requires the `GuildIntegrations` intent. Discord sends the guild id and nothing else — it does not say which integration changed or how — so nothing is cached and listeners that need the detail should call `guild.integrations.fetchAll()`
- `GUILD_SOUNDBOARD_SOUND_CREATE`, `GUILD_SOUNDBOARD_SOUND_UPDATE`, and `GUILD_SOUNDBOARD_SOUND_DELETE` dispatch handlers (`src/Events/SoundboardSounds.ts`), surfaced as the `SoundboardSoundCreate` / `SoundboardSoundUpdate` / `SoundboardSoundDelete` client events. Requires the `GuildExpressions` intent. Sounds are wrapped in the new `SoundboardSound` structure (`src/Structures/SoundboardSound.ts`, with an `emoji` accessor, `modify()`, and `delete()`) and cached per guild on `guild.soundboardSounds` (`src/Managers/SoundboardSounds.ts`, with `fetch(id)` / `fetchAll()` / `create()`). Discord includes `soundboard_sounds` in `GUILD_CREATE`, so the cache is seeded on connect rather than starting empty. Unlike every other guild expression the primary key is `sound_id` rather than `id`, so the structure exposes it as `soundId` and the cache is keyed on it; `SoundboardSoundDelete` therefore emits a bare `{ soundId }` object when the sound was not cached. A sound's icon is either a custom emoji (`emojiId`) or a standard unicode one (`emojiName`), never both, so the `emoji` accessor returns `undefined` for standard-emoji and iconless sounds rather than pretending they resolve. `fetchAll()` unwraps the `items` array this endpoint wraps its response in, which no other guild collection endpoint does
- `GUILD_SOUNDBOARD_SOUNDS_UPDATE` dispatch handler (`src/Events/SoundboardSounds.ts`), surfaced as the `SoundboardSoundsUpdate` client event, completing the soundboard family. Requires the `GuildExpressions` intent. Upserts every sound in the payload and derives individual `SoundboardSoundCreate` / `SoundboardSoundUpdate` events from the diff, then emits the batch once. Unlike the `GUILD_EMOJIS_UPDATE` handler it deliberately does **not** evict cached sounds absent from the payload: Discord does not document this event as a guaranteed full-list replacement, so treating an absence as a deletion risks silently dropping live sounds, and `GUILD_SOUNDBOARD_SOUND_DELETE` is the authoritative removal signal. The emitted `sounds` array is therefore only what the payload carried, not necessarily the guild's full soundboard — read `guild.soundboardSounds` for that
- `DiscordSoundboardSound` and its gateway payloads (`src/Types/DiscordAPITypes.ts`) — the soundboard sound object plus the `GUILD_SOUNDBOARD_SOUND_CREATE` / `GUILD_SOUNDBOARD_SOUND_UPDATE` / `GUILD_SOUNDBOARD_SOUND_DELETE` / `GUILD_SOUNDBOARD_SOUNDS_UPDATE` shapes. `DiscordGuildCreate` gains the `soundboard_sounds` field Discord has always sent but the type never modelled
- `DiscordGuildScheduledEvent` and its supporting types (`src/Types/DiscordAPITypes.ts`) — the scheduled event object, privacy level, entity types, status, entity metadata, and recurrence rule (frequency/weekday/month/n-weekday). These replace the `JSONObject` placeholders previously used for `DiscordInvite.guild_scheduled_event` and `DiscordAuditLog.guild_scheduled_events`, so `Invite.guildScheduledEvent` is now fully typed
- `DiscordIntegration` and its supporting types (`src/Types/DiscordAPITypes.ts`) — the integration object, its `type` union, expire behaviors, account and application sub-shapes, and the `INTEGRATION_CREATE` / `INTEGRATION_UPDATE` / `INTEGRATION_DELETE` / `GUILD_INTEGRATIONS_UPDATE` gateway payloads. These replace the `JSONObject[]` placeholder previously used for `DiscordAuditLog.integrations`
- `DiscordTeam` and `DiscordTeamMember` (`src/Types/DiscordAPITypes.ts`), with the `DiscordTeamMembershipStates` and `DiscordTeamMemberRoles` constants — the team that collectively owns an application, its members, and their invite state and role. These replace the `Record<string, JSONObject>[]` placeholder on `DiscordApplication.team`, which also had the wrong shape: Discord sends a single nullable team object rather than an array of members, so the field is now `DiscordTeam | null`
- `MessageInteractionMetadata` (`src/Types/Interactions.ts`) — a union discriminated on `type` over `ApplicationCommandInteractionMetadata` (adding `target_user` / `target_message_id`), `MessageComponentInteractionMetadata` (adding `interacted_message_id`), and `ModalSubmitInteractionMetadata` (adding `triggering_interaction_metadata`, narrowed to the two interaction kinds that can actually open a modal). This replaces the `JSONObject` placeholder on `DiscordMessage.interaction_metadata`, so the interaction a message was created in response to can be narrowed rather than cast

### Changed

#### `Message` no longer widens fields to `unknown`
- Five properties on the `Message` structure (`src/Structures/Message.ts`) were typed `unknown` even though the raw `DiscordMessage` type already modelled four of them precisely, so reading any of them meant a cast. They are now `member: Partial<DiscordMember> | null` (partial because Discord omits `user` there — it would duplicate the message's `author`), `mentionChannels: ChannelMention[]`, `interaction: MessageInteraction`, `components: MessageComponent[]`, and `interactionMetadata: MessageInteractionMetadata`. `member` also became optional, matching `patch()`, which only assigns it when the key is present — `unknown` had silently included `undefined`
- The `MESSAGE_CREATE` and `MESSAGE_UPDATE` handlers (`src/Events/Messages.ts`) take `member?: Partial<DiscordMember>` in place of `JSONObject`, matching the structure

#### Update events now emit a real "old" value
- Every `*Update` client event now emits a detached snapshot as its old value, so listeners can finally diff an update. Caches patch their entries in place — deliberately, so a reference captured earlier keeps tracking live state — which meant `cache.get()` followed by `cache.upsert()` handed listeners the *same, already-mutated* object twice. `PresenceUpdate` was the only handler that avoided this. Affects `MemberUpdate`, `GuildUpdate`, `ChannelUpdate`, `ThreadUpdate`, `RoleUpdate`, `GuildScheduledEventUpdate`, `AutoModerationRuleUpdate`, `IntegrationUpdate`, `SoundboardSoundUpdate`, `EmojiUpdate`, and `StickerUpdate`. The old value is still `undefined` when the entity was not previously cached, so no signature changed
- `clone()` on `APIClientStructure` and `APIGuildStructure` (`src/Contracts/DiscordStructure.ts`) — copies a structure's own fields onto a fresh instance of its class, then calls a `protected detach()` hook. The snapshot is deliberately **shallow**: identity and shared infrastructure (the client, the owning guild, a guild's 13 sub-caches, a thread's member cache) stay aliased to the live instance, since `GUILD_UPDATE` only ever changes a guild's own fields and copying every member on each one would be ruinous. This works because nearly every `patch()` *reassigns* its fields rather than mutating them, so a shallow copy already diverges on the next patch; `detach()` exists for the handful that do not — `Role.permissions` (a `BitField` updated via `override()`), a channel's `permissionOverwrites` manager, and `Member.user` (the shared cached `User`, so a username change arriving on `GUILD_MEMBER_UPDATE` is now diffable). `Presence.clone()`'s bespoke implementation was folded onto this shared one
- The lazily-created `MessageManager` behind `channel.messages` (`src/Mixins/Channels/Messageable.ts`) and the cached DM channel behind `user.send()` (`src/Structures/User.ts`) moved from `#private` fields to module-level `WeakMap`s. `clone()` builds its copy without running the constructor and so cannot carry private fields across; a clone would have thrown on first access. Both are lazy caches, so a snapshot simply starts without one and builds its own. They remain just as inaccessible from outside the module

#### Buttons no longer require a label

- **Breaking (types).** `label` on `InteractiveButton` and `LinkButton` (`src/Types/Components.ts`) is now optional. Discord requires *at least one of* `label` and `emoji`, so an emoji-only icon button was previously impossible to express — the type demanded a label and `validateButtonLabel()` threw without one. `PremiumButton` is unaffected; it derives from neither field
- `validateButtonLabel()` was replaced by **`validateButtonContent(button)`** (`src/Builders/ButtonBuilder.ts`), which takes the whole button rather than just its label and throws `"Button must have a label or an emoji"` when both are absent. The 80-character ceiling now applies only when a label is actually present. Renamed rather than kept, since it no longer checks only the label; both are public exports, so this is a breaking rename
- `setEmoji()` on both button builders now rejects an emoji that identifies nothing. Every field of `ComponentEmoji` is optional, so presence alone proves nothing — a custom emoji is identified by `id` and a unicode one by `name`, and `{}` or `{ animated: true }` would render a blank face. This also brings `setEmoji()` in line with the other setters, which all validate

#### Polls can be sent with a message

- **Breaking (types).** `MessagePayload.poll` (`src/Types/Internal.ts`) was added, typed `PollCreateRequest`. A poll could previously be *received* on a `Message` and *sent* on an interaction response, but there was no way to send one through `channel.send()`, `message.reply()`, or `webhook.send()` at all. `CreateMessagePayload()` counts a poll as content, so a poll-only message is no longer rejected as empty
- Consequently the v1/v2 mixing rule that rejects a poll alongside Components V2 (`src/Builders/ComponentsV2.ts`) is now live on every send path. It was previously unreachable there: `MessagePayload` had no `poll` field, so the check could only be exercised by casting a payload past the compiler
- `PollCreateRequest` moved from `src/Types/Interactions.ts` to `src/Types/MessageComponents.ts`, beside `Poll`, `PollAnswer`, `PollMedia`, and `PollLayoutTypes`. It is no longer interaction-specific, and both `Types/Internal.ts` and `Types/Interactions.ts` already imported from `MessageComponents.ts`, so this avoids a new import cycle rather than creating one. The public surface is unchanged — both files are `export *`'d from `Types/index.ts`
- **Breaking (types).** `poll` is excluded from the edit payloads of `message.update()`, `webhook.editMessage()`, and `webhookMessage.update()`, alongside the `sticker_ids` and `message_reference` already excluded there. Discord's Edit Message endpoint does not accept one

#### Modal response types match what the builder actually sends

- **Breaking (types).** `InteractionCallbackModal.components` (`src/Types/Interactions.ts`) narrowed from `ModalComponent[]` to `Label[]`. The type accepted the legacy `ActionRow` while `ModalBuilder` threw on one unconditionally, so the compiler admitted a payload that always failed at runtime in `showModal()`
- The **inbound** types are deliberately unchanged: `ModalSubmitData.components` and `ModalInteraction.fields` still accept `ModalComponent`, because Discord genuinely returns action rows on a `MODAL_SUBMIT`. Narrowing those would assert something about Discord's behaviour rather than about this library's. `assertLabelComponent()` correspondingly stays a runtime guard, for JavaScript callers and for anything built from an inbound submission

#### `ephemeral` is only accepted where it can take effect

- **Breaking (types).** `interaction.editReply()` and a component interaction's `update()` no longer accept `ephemeral`. A response's visibility is fixed when the interaction is first answered, so neither editing the original response nor editing the message a component is attached to can change it — the key was accepted and then silently ignored. The two callbacks that send a *new* message, `reply()` and `followUp()`, still take it; to make a *deferred* response ephemeral, pass it to `deferReply()`, where the flag actually has to be set
- `InteractionReplyMessages` (`src/Types/Interactions.ts`) — `InteractionCallbackMessages` plus `ephemeral`, which is what splits the two groups of callbacks apart at the type level. `InteractionCallbackMessages` itself no longer carries the key
- `src/Mixins/Interactions/ResolvePayload.ts` — the payload normalizers both interaction mixins now share, exported from the barrel: `ResolveReplyPayload()` / `InteractionReplyPayload` for the callbacks that send a new message and `ResolveEditPayload()` / `InteractionEditPayload` for the ones that edit an existing one. `InteractionReplyPayload` moved here from `src/Mixins/Interactions/Repliable.ts`, keeping its name and its public export path; `Repliable` and `Updateable` each carried their own copy of the same resolver before
- Interaction response coverage (`src/Tests/Interactions.test.ts`) — that `reply()` and `followUp()` set the `EPHEMERAL` flag and send no `ephemeral` field, that an ephemeral reply keeps its Components V2 flag alongside the ephemeral bit, and a type-level check that `editReply()` and `update()` reject the key

### Fixed

- **`attachments: []` now clears a message's attachments.** `SplitAttachments()` (`src/Structures/Message.ts`) destructured `attachments` out of the payload and returned early on an empty list, producing a body with no `attachments` key — indistinguishable from omitting the field. Since an explicit empty array is Discord's *only* way to say "remove every attachment", `message.update({ content: "x", attachments: [] })` silently kept every file. The three states are now distinct: omitted leaves the existing files alone, a list keeps exactly those, and `[]` removes them all
- **Attachment limits now count retained attachments.** `ValidateFiles()` in `src/Rest.ts` only ever sees the uploads, so an edit keeping 8 existing files while adding 5 passed local validation with 13 attachments on the wire, and a new `a.png` uploaded alongside a *retained* `a.png` was accepted — exactly the ambiguous `attachment://a.png` the uniqueness rule exists to prevent. A new `ValidateAttachments()` runs inside `SplitAttachments()`, which is the one place that sees both halves, enforcing `MAX_MESSAGE_ATTACHMENTS` (10) and name uniqueness across uploads and retained entries together. `ValidateFiles()` remains as the transport-level backstop for anything calling `client.rest` directly. A retained attachment with no `filename` keeps whatever it is currently called, which is not knowable client-side, so it is skipped for the uniqueness check rather than guessed at — a per-entry skip, unlike `validateAttachmentReferences()`, which abandons its check entirely, because that one proves a negative
- **`src/Builders/ComponentsV2.ts` is exported.** `src/Builders/index.ts` re-exported every sibling file except this one, leaving `MAX_V2_COMPONENTS`, `MAX_V2_CONTENT_LENGTH`, `ComponentSummary`, `SummarizeComponents`, and `ResolveComponentsV2Flags` invisible to consumers while `PreparePayload` and `SplitAttachments` were already public. `ComponentsV2Payload` was also exported, since it is `ResolveComponentsV2Flags`'s parameter type and the function was otherwise unusable
- `PollMedia.text` (`src/Types/MessageComponents.ts`) was missing entirely, which made `PollCreateRequest` unconstructible — the question and every answer require it when creating a poll, even though Discord omits it from some responses
- **`ephemeral` no longer rides onto the wire as an unknown field.** `Repliable.reply()` translated the key into the `EPHEMERAL` flag but left it in the body it sent, and `followUp()` never translated it at all, so a follow-up was public however it was asked for. Both now go through `ResolveReplyPayload()`, which drops the key while setting the flag — only `attachments` is stripped further down the send path, so anything else left in the payload reaches Discord
- **`REACTION_ADD` no longer upserts an absent member.** The handler (`src/Events/Reactions.ts`) tested `'member' in data` before upserting, which is true for a key explicitly present as `undefined` and would have put a junk entry in the guild's member cache; it now tests the value itself
- **`WEBHOOKS_UPDATE` no longer casts a missing guild into one.** The handler (`src/Events/Webhooks.ts`) asserted `ResolveLocation()`'s nullable guild as a `Guild | { id }`, so a listener typed against the event could read fields off `null`. It now falls back to `{ id: data.guild_id }`, which makes an unresolved guild a degraded payload rather than a lie — the same shape the other location-resolving events emit
- Handler coverage for the five registered events with no test of their own (`src/Tests/GatewayEvents.test.ts`): `StickersUpdate` (which shipped a naming bug with nothing to pin it), `InviteCreate`, `InviteDelete`, `MessageDeleteBulk`, and `TypingStart`, plus a check that every `ClientEvents` value equals its key

### Fixed

- `patch()` no longer blanks a cached structure when handed a partial payload. Discord types a number of fields as always present but sends partial objects on nested payloads, and the fields carrying `!` definite-assignment markers were assigned unconditionally, so upserting a partial would overwrite real values with `undefined`. They are now guarded exactly like the optional fields alongside them, which covers future partial payloads rather than relying on each call site to guard. The `!` markers still hold: a structure is only ever constructed from a full payload, so a partial one can now only leave those fields untouched. Applied to:
  - `User` (`src/Structures/User.ts`) - `id`, `username`, `discriminator`, `global_name`, `avatar`. `PRESENCE_UPDATE` carries a user object with only `id`; `PresenceUpdate` already guarded at the call site
  - `Member` (`src/Structures/Member.ts`) - `deaf`, `mute`, `flags`, `roles`, `joined_at`, `user`. An interaction's `resolved.members` omit all three of `user`, `deaf`, and `mute`, and the missing `user` was worse than a blanking: `patch()` called `client.users.upsert(data.user)` unconditionally and threw
  - `Guild` (`src/Structures/Guild.ts`) - the thirteen unconditional fields from `id` through `premium_progress_bar_enabled`, for partials such as an invite's `guild`
  - `Emoji` (`src/Structures/Emoji.ts`) - `id`, `name`, `animated`, `available`, for the partial emoji on a reaction payload
  - `Sticker` (`src/Structures/Sticker.ts`) - `id`, `name`, `tags`, `type`, `format_type`, for the sticker items on a message
  - `BaseChannel` (`src/Structures/Channels/BaseChannel.ts`) - `id` and `type`. Every partial channel Discord sends carries both, so this one is purely defensive; the channel subclasses already guarded their own fields
- `Guild.patch()` no longer throws on a payload without a `roles` array. It iterated `data.roles` unconditionally while `channels`, `members`, `stickers`, `emojis`, and `soundboard_sounds` were all guarded, so any partial guild object crashed rather than being merged
- REST rate limiting is no longer reactive-only. An `X-RateLimit-Remaining: 0` on any response now records the bucket's reset window pre-emptively, and requests sharing a rate limit key are serialized through a per-bucket queue, so a burst of concurrent calls paces itself instead of all passing the limit check together, hitting Discord together, and coming back `429` together
- A global rate limit now pauses every bucket. It was recorded but only ever honoured by clients running with `perRouteRateLimits` disabled
- `WSClient.#reconnect()` no longer retries immediately and forever. Reconnects are scheduled with exponential backoff and full jitter (1s base, 60s cap, first attempt still immediate) and stop after `maxReconnectAttempts`. Fatal close codes (4004 authentication failed, 4010–4014 invalid shard/sharding required/invalid API version/invalid or disallowed intents) now stop reconnecting entirely instead of replaying a rejected `IDENTIFY` in a tight loop, and `4007`/`4009` drop the stale session so the next connection identifies rather than resuming
- `GatewayOpCodes.InvalidSession` now waits Discord's mandated randomized 1–5 seconds before reconnecting, instead of re-identifying instantly and burning the session start rate limit
- `Client.login()` now rejects with the gateway's actual failure reason when the connection is rejected outright (bad token, disallowed intents), instead of waiting the full ten seconds to blame a Discord outage
- `eslint.config.ts` imports `Plugin` from `@eslint/core` as a type-only import, since that package only ships types and no runtime logic
- All builders now implement their corresponding JSON payload interface directly, for improved type safety
- Minimum supported Node version raised from 18 to 20, matching what the test suite actually requires
- **Breaking:** structure and type fields renamed from Discord's wire-format snake_case to camelCase with an `Id` suffix across the library (e.g. `channel_id` → `channelId`, `guild_id` → `guildId`, `mention_everyone` → `mentionEveryone`), for consistency with the rest of the public API
- `GuildBanManager.delete()` now takes a user id instead of unbanning the whole guild
- Invite `fetch()`/`delete()` now hit `/invites/:code` instead of a nonexistent guild-scoped route
- `Member.timeoutUntil(null)` now sends `null` instead of the current timestamp
- `Member.setNickname()` now sends the `nick` field instead of `nickname`
- Guild ban event handlers no longer assume the guild is cached
- Default avatar URLs now resolve under `/embed/avatars/` instead of an incorrect path
- `User.avatarURL()` now only returns a `.gif` extension for avatars with an animated hash
- REST requests now target Discord API v10 and include a `User-Agent` header
- `Message.react()` now URL-encodes the emoji with `encodeURIComponent` instead of `encodeURI`
- `ReactionAdd` now looks up the channel by channel id instead of guild id
- Channel permission overwrites, position, and topic no longer crash on partial channel payloads
- `Message.patch()` now updates `guildId` and `member` instead of locking them to their first-seen value
