# AGENTS.md

## Project snapshot
- `SimplyJS` is a TypeScript-first Discord library (`package.json` description: minimal `discord.js` alternative).
- Current implementation is still type- and protocol-heavy, but runtime layers are no longer fully empty: `src/Client.ts` wires auth/login/destroy with top-level caches (`GuildCache`, `UserCache`), `src/WSClient.ts` has gateway handshake/heartbeat/event dispatch logic, `src/Rest.ts` has authenticated `GET`/`POST`/`PATCH`/`DELETE`/`PUT` helpers, and `src/EventDispatcher.ts` routes gateway events using handlers exported from `src/Events/index.ts`.

## Architecture and data flow (what exists now)
- Core protocol constants are centralized in `src/Types/DiscordGateway.ts` (`GatewayOpCodes`, `GatewayIntents`, `GatewayEvents`, `GatewayPayload`).
- Runtime bootstrapping currently flows through `src/Client.ts`: constructor sets token on both `WSClient` and `Rest`, resolves intents via `ResolveIntents`, instantiates top-level caches (`GuildCache`, `UserCache`), and exposes `login()` / `destroy()`. `login()` polls `socket.ready`; `destroy()` calls `socket.destroy()` and polls until disconnected.
- `WSClient` stores resolved intents on `socket.intents`, and Identify in `WSClient.#handleHello` sends `this.intents`.
- `WSClient` extends `EventEmitter<WSEvents>` (typed events mirroring `GatewayOpCodes`: `RAW`, `HEARTBEAT`, `RECONNECT`, `INVALID_SESSION`, `HELLO`, `HEARTBEAT_ACK`) and creates a dispatch function with `CreateDispatch()`; gateway dispatches flow through `this.dispatch(this.client, data.t, data.d)`.
- `WSClient` tracks `session_id`/`resume_gateway_url` from `READY` and heartbeat ACK state; `GatewayOpCodes.Reconnect`/`InvalidSession` and an unacked heartbeat all route through `WSClient.#reconnect()`, which resumes via `GatewayOpCodes.Resume` when a session is available and re-identifies otherwise. `#reconnect()` schedules the retry rather than reconnecting inline: the first attempt is immediate, each consecutive failure backs off exponentially with full jitter (1s base, 60s cap), op 9 always waits the mandated 1-5s, and the client gives up after `maxReconnectAttempts` (default 10) or on a fatal close code (`GatewayCloseCodes`: 4004, 4010-4014), emitting `WSEvents.Disconnect`. The counter resets on `READY`/`RESUMED`. `RESUMED` is the one dispatch that does not reach the shared `this.dispatch(...)` call at the end of `#handleMessage`: it carries a null `d`, and that call sits behind a `!data.d` guard, so its own branch dispatches it with an empty object and returns. Any other payload-less dispatch has to do the same. `WSEvents.Resumed` stays the socket-level signal and `ClientEvents.Resumed` is the public one, the same split `READY`/`Ready` has.
- `src/Collector.ts` provides `createCollector(emitter, event, options)` / `awaitEvent(emitter, event, options)` — filtered, self-cleaning temporary listeners (`time`/`idle`/`max` bounds) built on `Collector extends EventEmitter`. Overloads are defined for `Client` and `WSClient` specifically (see the comment in that file) because TypeScript can't infer the event map generic through node's `EventEmitter<T>` when the argument is a subclass instance.
- Intent normalization helpers (`ResolveIntents`, `HasIntent`) in `src/Intents.ts` convert mixed user input (number, key names, numeric array) into a bitfield. `HasIntent`'s one internal use is `MemberCache.fetchGateway()`, which checks `client.socket.intents` before sending.
- Gateway requests that get an answer (currently only `RequestGuildMembers`, op 8) correlate replies with a nonce rather than a pending-request map on `WSClient`: the caller generates a nonce, attaches a `Collector` filtered on it, *then* sends. `MemberCache.fetchGateway()` (`src/Managers/Members.ts`) is the reference implementation — `WSClient.requestGuildMembers()` is the raw fire-and-forget send, `MembersChunk` (`src/Events/Members.ts`) does the caching and emits `ClientEvents.GuildMembersChunk`, and the collector stops on `chunkIndex === chunkCount - 1` or rejects on its own `time` timeout. Keeping the state in the collector rather than on the socket means a reconnect cannot leak a pending promise.
- Gateway dispatch flows: `WSClient.#handleMessage` → `CreateDispatch()` result from `src/EventDispatcher.ts` → handler module exported from `src/Events/index.ts` (e.g., `GuildCreate`) → updates `Client` cache or structure in `src/Structures/` (channel classes live under `src/Structures/Channels/`) or `src/Managers/`.
- Gateway handlers then emit the public client event surface from `src/Types/SimplyJSTypes.ts` (`ClientEvents` / `ClientEventMap`) via `Client.emit(...)`.
- `Client.guilds` and `Client.users` are top-level caches (`GuildCache`, `UserCache`, both extending `GlobalCache<string, V, API>`); `fetch(id)` uses REST and `upsert()` to patch/create entries, and `Guild` owns nested caches for `channels`, `roles`, `emojis`, `stickers`, `members`, `webhooks`, and others (all constructed at the top of the `Guild` constructor, before `patch()` runs).
- Threads are not a separate collection: they live in the guild's `ChannelCache` alongside every other channel, and `BaseChannel.isThreadChannel()` narrows to `GuildThreadChannel`. Each `GuildThreadChannel` in turn owns a `ThreadMemberCache` (`src/Managers/ThreadMembers.ts`) on `thread.members`, keyed by user id — the one cache that hangs off a channel rather than a `Guild`. It is still a `GuildScopedCache`, so it takes the owning guild as well as the thread. `GuildThreadChannel` assigns it inside `patch()` with `??=` rather than a field initializer, because `patch()` runs from `BaseChannel`'s constructor, before subclass field initializers would execute under `useDefineForClassFields`.
- Not every manager is a cache. `GuildBanManager` (`src/Managers/GuildBans.ts`), `GuildInviteManager` (`src/Managers/Invites.ts`), `MessageManager` (`src/Managers/Messages.ts`), and `ThreadManager` (`src/Managers/Threads.ts`) are plain classes rather than `GlobalCache`/`GuildScopedCache` subclasses — they hold a `client` and their owning scope, and every method goes straight to REST. `MessageManager` is cacheless by design: a channel's message history is unbounded, so caching it would mean owning an eviction policy. It hangs off a channel rather than a guild, and is reached through the `messages` accessor on the `Messageable` mixin (`src/Mixins/Channels/Messageable.ts`), which creates it lazily from a module-level `WeakMap` so a `GUILD_CREATE` burst does not allocate one per channel. `ThreadManager` reaches channels the same way, through the `threads` accessor on the `Threadable` mixin (`src/Mixins/Channels/Threadable.ts`, applied to `GuildTextChannel` / `GuildAnnouncementChannel` / `GuildForumChannel`); it is cacheless because threads *are* channels, so everything it creates or lists is upserted into `guild.channels`. Because these mixins return `as unknown as Constructor<MessageableClass<...>>`, anything added to a mixin body must also be declared on its `*Class<T>` type or it stays invisible on the channel classes.
- `Webhook` (`src/Structures/Webhook.ts`) is an `APIClientStructure`, not an `APIGuildStructure`, because a webhook fetched by token has no guild. Its `WebhookCache` (`src/Managers/Webhooks.ts`) is still guild-scoped and lives on `guild.webhooks`. Every webhook action picks its route from whether `this.token` is set — `/webhooks/{id}/{token}` needs no bot authorization but cannot move the webhook between channels, `/webhooks/{id}` needs `MANAGE_WEBHOOKS`. `src/Rest.ts` already buckets both shapes correctly (see the `resource === "webhooks"` case in the rate limit key). The *message* routes are the exception to that route-picking rule: `/webhooks/{id}/{token}/messages/{id}` has no bot-authenticated equivalent, so `fetchMessage()`/`editMessage()`/`deleteMessage()` all go through `#requireToken()` and throw without one. They share `WebhookMessageRoute()` (`src/Structures/WebhookMessage.ts`), which carries the `thread_id` query — a threaded message is `404` on the unqualified route. `webhook.send()` returns a `WebhookMessage`, not a `Message`, because the inherited `update()`/`delete()` are both wrong for a webhook-authored message; new webhook send paths must keep returning that subclass rather than a bare `Message`.
- `src/Rest.ts` keeps route/bucket rate-limit state in `src/DataStructures/TTLCache.ts` (`routeRateLimits`, `routeToBucket`) and exposes `RestOptions` for `retryAfterRateLimit`, `rateLimitDurationMultiplier`, and `perRouteRateLimits`. Rate limiting is pre-emptive, not just reactive: `X-RateLimit-Remaining: 0` on *any* response records the bucket's reset window, requests are serialized per rate limit key through an internal promise-chain queue (`#enqueue`, skipped when `perRouteRateLimits` is off), and a global limit blocks every bucket.
- Uploads go through `src/Rest.ts` as `multipart/form-data`: `post()`/`patch()`/`put()` take a fourth argument that is either a bare `FileAttachment[]` or a `{ files, multipart }` `MultipartUpload`. `MultipartMode` picks the form layout — `payload_json` (the default) puts the whole JSON body in a `payload_json` part with one `files[n]` part per file, which is what message, webhook, and interaction endpoints want; `fields` flattens the body into individual form fields with the single file under a part named `file`, which sticker creation requires and which rejects more than one file up front since they would share a part name. `BuildFormData` is called per attempt, not per request: a body handed to `fetch` is consumed and cannot be replayed on a `429`/`5xx` retry. Everything else (queueing, rate limits, backoff) is shared with JSON requests.
- Upload helpers live in `src/Utils.ts`: `DetectMimeType()` reads the type from magic bytes (never a filename — nothing here touches the disk, and an extension is only a claim) and covers PNG/GIF/JPEG/WebP, Lottie JSON, and MP3/OGG audio - MP3 is the one type with no signature to match when it carries no ID3 tag, so an untagged file is identified by validating every fixed field of its opening frame header, since the sync bits alone also match a UTF-16LE byte order mark; `ToDataURI()` encodes the base64 data URI Discord's JSON image fields want and passes an already-encoded one through; `EncodeImage()` is its nullable wrapper for the optional image fields of an edit, where `undefined` leaves the image alone and `null` clears it, so both pass straight through; and `ResolveUpload()` names a file for the form from the name of the thing being created plus the detected extension. `UploadInput` (`Buffer | Uint8Array`, `src/Types/Internal.ts`) is what endpoints take when Discord ignores the filename, as opposed to `FileAttachment` for message attachments where the name is load-bearing for `attachment://` references; `ImageInput` (`UploadInput | string`) is the same thing for a JSON image field, where an already-encoded data URI is also accepted. Every JSON image field takes `ImageInput` and encodes on the way out — guild icon/splash/discovery splash/banner, role icons, scheduled event images, webhook avatars, and soundboard sounds — alongside the multipart consumers `EmojiCache.create()` and `StickerCache.create()`; new resource-upload endpoints should reuse these rather than re-deriving types.
- Every send path funnels through `PreparePayload()` in `src/Structures/Message.ts` — `channel.send()`, `message.reply()`/`.update()`, `user.send()`, `webhook.send()`, `ThreadManager.createForumPost()`, and the `Repliable`/`Updateable` interaction mixins. It runs `ResolveComponentsV2Flags()` (`src/Builders/ComponentsV2.ts`) and then `SplitAttachments()`, which splits a payload into the JSON body and the `FileAttachment[]` to upload, replacing each attachment with an `{ id, filename?, description? }` descriptor. Flags are returned rather than set, so the caller's own payload is never mutated; they land on the copy `SplitAttachments()` makes. New send paths must call `PreparePayload()` rather than `SplitAttachments()` directly, or the Components V2 rules become skippable.
- `ResolveComponentsV2Flags()` is the only automatic inspection of a payload on the way out — the per-component `validate()` methods stay opt-in and nothing on the send path calls them. It enforces only what a single component cannot see for itself: whether the message is v2 at all, the v1 features it may then no longer carry (`content`, `embeds`, `sticker_ids`, `poll`), the message-wide budgets (40 components including nested ones, 4000 characters across every `TextDisplay`), and whether each `attachment://` reference names a file actually being uploaded. One recursive pass (`SummarizeComponents()`) collects all of it. `ACTION_ROW` is deliberately not counted as a v2-only type, so an action-row-only payload stays a v1 message. Edits pass the edited message's flags as the second argument so a message that is already v2 stays held to the v2 rules; `Repliable.editReply()` cannot, since it addresses the original response by token and never sees its flags.
- The interaction response mixins split their payload types by what the callback can actually do. `src/Mixins/Interactions/ResolvePayload.ts` holds both normalizers: `ResolveReplyPayload()` / `InteractionReplyPayload` for the callbacks that send a new message (`Repliable.reply()`, `followUp()`), and `ResolveEditPayload()` / `InteractionEditPayload` for the ones that edit an existing one (`Repliable.editReply()`, `Updateable.update()`). Only the send side accepts `ephemeral`, since a response's visibility is fixed when the interaction is first answered; `ResolveReplyPayload()` translates it into `MessageFlags.EPHEMERAL` and **drops the key**, because Discord has no `ephemeral` field and `SplitAttachments()` only strips `attachments` — anything else left in a payload reaches the wire. A new interaction response must route through one of the two rather than resolving a string payload itself.
- Abstract base classes in `src/Contracts/` define the structural contracts:
  - `APIClientStructure<T>` — client-bound structures needing `client` access (holds `protected readonly client: Client`)
  - `APIGuildStructure<T>` — guild-owned structures needing both `client` and `guild` access (holds `protected readonly client: Client` and `protected readonly guild: Guild`)
  - Both structure bases also provide a concrete `clone()` plus a `protected detach(source)` hook. `upsert()` patches cached entries **in place** so earlier references keep tracking live state, which means every `*Update` handler must take a `cache.get(id)?.clone()` snapshot *before* upserting or it will emit the same mutated object as both `old` and `new`. `clone()` copies own fields onto a bare instance of the class: it carries no `#private` fields (use a module-level `WeakMap` for lazy caches, as `Messageable`/`User` do) and shares sub-caches and the `client`/`guild` refs with the original. Override `detach()` only for state `patch()` mutates rather than reassigns — see `Role.permissions` and the `PermissionOverwrites` mixin.
  - `GlobalCache<K,V,API>` / `GuildScopedCache<K,V,API>` — typed Maps with `abstract upsert(data: API): V` and `abstract fetch(key: K): Promise<V>` for top-level and guild-scoped caches respectively
- Domain model types for Discord REST/gateway payloads are in `src/Types/DiscordAPITypes.ts` and `src/Types/MessageComponents.ts`.
- Gateway packet envelope typing (including Hello/Ready payload shapes) is in `src/Types/DiscordGateway.ts` via `GatewayPayload<T>`.
- `src/Types/Internal.ts` defines event contracts (`EventHandler`) plus `defineEvent(...)` for strongly typed handler declarations.
- `src/Types/Internal.ts` also defines `JSONPrimitive`, `JSONValue`, `JSONObject` used by `Rest` method signatures.
- Shared utility types (`ObjectValues`, `DeepPartial`, `Awaitable`) are in `src/Types/HelperTypes.ts` and are reused across type modules.
- `src/EventDispatcher.ts` `CreateDispatch(...)` builds a handler map from `src/Events/index.ts` exports, detects duplicate event names, supports optional per-event overrides (used in tests), and invokes async handlers via `void handler(...)`.

## Conventions specific to this repo
- Structure/type fields use camelCase with an `Id` suffix (`channelId`, `guildId`, `webhookId`), not Discord's wire-format snake_case (`channel_id`) — the wire format is only used at the REST/gateway payload boundary, before it's parsed into a structure.
- Use ESM imports with explicit `.js` suffix even in `.ts` source (example: `import { GatewayEvents } from "./Types/DiscordGateway.js"`).
- Prefer `const` object maps + `as const` for enum-like values (seen across `src/Types/*.ts`) rather than TypeScript `enum`.
- Derive value unions from maps using `ObjectValues<typeof X>` for API field typing.
- Keep heavy inline API documentation/comments close to exported types; this codebase treats docs as part of source-of-truth.
- Treat `CODE_STYLE_AND_RULES.md` as a required guide for every future edit; follow its rules for JSDoc, getter boundaries, and code-style expectations before making changes.
- Structure `patch(data)` methods use `if ("key" in data && data.key !== undefined)` guards for **every** field, including the ones Discord types as required and that carry `!` definite-assignment markers — nested payloads carry partial users, members, guilds, channels, emojis, and stickers, and an unconditional assignment would blank a cached structure (or, where `patch()` dereferences the value, throw). The `!` markers still hold, since a structure is only ever constructed from a full payload. Arrays that `patch()` iterates need the same guard (see `Guild.patch()`'s `roles`/`emojis`/`members` loops). `src/Tests/PartialPayloads.test.ts` is the regression surface for this.
- New event handlers go in `src/Events/` as named `const` exports created with `defineEvent(...)` from `src/Types/Internal.ts`; export them from `src/Events/index.ts` so `EventDispatcher` can register them.
- New domain structures extend `APIClientStructure<T>` or `APIGuildStructure<T>` from `src/Contracts/DiscordStructure.ts`, depending on whether the structure is client-bound or guild-owned.
- New top-level caches extend `GlobalCache<K,V,API>` from `src/Contracts/CacheStructure.ts` and must implement `upsert(data)` and `fetch(key)`.
- Builders in `src/Builders/` **are** their wire payloads: each one `implements` the payload type it builds (`ButtonBuilder implements InteractiveButton`, `ModalBuilder implements InteractionCallbackModal`, ...) and stores fields under their snake_case wire names (`custom_id`, `min_values`, `default_values`). There is deliberately no `toJSON()` — a builder can be sent, inspected, cloned, or logged as-is, and nested builders need no conversion. Every builder also exposes a static `from(value)` and both a static and an instance `validate()`, which read the same wire shape.
  - **Every** component builder extends the abstract `ComponentBuilder` in `src/Builders/ComponentBuilder.ts`, which holds the optional `id` field every component shares plus a `setId()` validated as a 32-bit integer — the Components v2 builders (`TextDisplayBuilder`, `ThumbnailBuilder`, `SectionBuilder`, `MediaGalleryBuilder`, `FileBuilder`, `SeparatorBuilder`, `ContainerBuilder`), `ActionRowBuilder`, the three button builders, all five selects through `BaseSelectBuilder`, and the modal pair (`TextInputBuilder`, `LabelBuilder`). Each carries `id` through its static `from()` and checks it from `validate()` via `validateComponentId()`, so a new builder should do both. `id` is not an alternative to `custom_id`: `custom_id` routes the interaction back to you, `id` addresses the component for editing and ordering. The v2 builders' tests live in `src/Tests/ComponentsV2.test.ts`, kept separate from the v1 `src/Tests/Components.test.ts`.
  - The media-bearing builders share `src/Builders/UnfurledMedia.ts`: `ResolveMedia()` normalizes a bare url string into an `UnfurledMediaItem`, and `ValidateMedia()` / `ValidateMediaDescription()` hold the checks. A builder that nests others (`SectionBuilder`, `ContainerBuilder`) splits its child checks in two — an eager type assertion in every setter, since a wrong child type is a structural mistake, and the full `validate()` on the child deferred to the owner's own `validate()`, so a half-built child can still be added and filled in afterwards. The eager assertion is the real guardrail, since nothing on the send path calls a child's `validate()`. Each owner's static `from()` asserts *before* mapping a child to its builder, so an unsupported child is reported as itself rather than as the `undefined` the mapping falls through to.
  - Colors go through `ResolveColor()` in `src/Utils.ts` (`number | "#RRGGBB"`), shared by `EmbedBuilder.setColor()` and `ContainerBuilder.setAccentColor()`.
  - Corollary: a builder must have **no** own enumerable property that isn't part of the payload, or it leaks to Discord as an unknown key. Put internal state on the prototype (e.g. the `protected get selectLabel()` accessor in `src/Builders/BaseSelectBuilder.ts`) or in a `#private` field. `src/Tests/Components.test.ts` pins this.

## Tooling and workflows
- Type/lint check: `npm run check` (runs ESLint + `tsc --noEmit`).
- Build: `npm run build` (lint + typecheck + `tsc --noEmit` + `tsup`, outputs ESM/CJS + d.ts to `dist/`).
- Tests: `npm test` (`vitest run`), with test discovery configured as `src/Tests/**/*.ts` in `vitest.config.ts`.
  - Gateway tests drive a hoisted `MockWebSocket` (`src/Tests/WSClient.test.ts`) that records every frame in `sent` and exposes `emitMessage()` / `emitRaw()` / `close()` / `emitError()` to play the gateway's side. It closes *synchronously*, unlike a real socket, so a test asserting a timer was cleared should count `vi.getTimerCount()` rather than infer it from a socket that never opened — `#reconnect()`'s callback returns early when destroyed, which makes a timer that fires and is ignored look exactly like one that was cancelled.
- Examples are **not** covered by any script or by CI: `eslint.config.ts` ignores `examples/**`, and neither `npm run check` nor the workflows typecheck them. Check them by hand with `npx tsc --noEmit -p examples/tsconfig.json` after touching anything under `examples/`.
- Raw linting: `npm run lint` (library only), auto-fix with `npm run lint:fix`.
- Post-release backlog lives in `TODO.md`: add ideas as unchecked checklist items (`- [ ] ...`), and in the PR that ships an item, mark it complete in `TODO.md` (`- [x] ...`).
- Treat `TODO.md` as an active product backlog, not a passive notes file: future agents should proactively add missing features, follow-up work, and cleanup items there, then mark them complete when they are shipped.
- Release history lives in `CHANGELOG.md`. Add a new `## [version] - YYYY Month D` heading at the top for each release, matching the prose dates already in the file, with `### Added`, `### Changed`, `### Fixed`, and `### Removed` subsections as needed (omit empty ones). Work in progress goes under the `## [unreleased]` heading at the top, and large releases group their bullets under `####` feature subheadings.
- A deleted public export needs a `### Removed` entry of its own. A **Breaking** bullet under `### Changed` covers surface that changed shape; it does not cover surface that is gone, and a removal with no entry is how `EventRequiredIntent` vanished in 1.2.0-alpha unrecorded.
- CI (`.github/workflows/{node.js,bun,deno}.yml`) runs build + test on Node 20/22/24, Bun, and Deno. There is no publish/release workflow and no examples check.

## Lint rules agents must respect
- Custom ESLint rule `local/require-unref-on-timers` in `eslint.config.ts` requires `setTimeout(...).unref()` / `setInterval(...).unref()` chaining.
- `@typescript-eslint/no-floating-promises` is `error`; do not leave unhandled promises.
- Unicorn rules enforced include `unicorn/no-array-for-each` (prefer `for...of`), `unicorn/prefer-node-protocol` (use `node:` imports), and `unicorn/no-process-exit`.

## Integration boundaries
- External runtime deps are currently minimal: `ws` (gateway transport candidate).
- Discord API vocabulary is pinned locally via constant/type files (`src/Types/DiscordGateway.ts`, `src/Types/DiscordOAuth.ts`, `src/Types/DiscordAPITypes.ts`) instead of pulling from a generated SDK.
- Package entrypoints are dual-format (`package.json` `main`: `dist/index.cjs`, `module`: `dist/index.js`) with conditional `exports` for ESM/CJS consumers, and `src/index.ts` is the active public barrel export.

## Practical guidance for new agents
- Review `CODE_STYLE_AND_RULES.md` before editing code so new changes stay aligned with the documented style and behavioral rules.
- Check `TODO.md` when planning work; if you discover an obvious missing feature or cleanup item while editing, add it there so the backlog stays current.
- Implement runtime behavior by extending existing typed protocol surfaces first (start from `GatewayPayload`, `GatewayEvents`, `src/Intents.ts`).
- When adding new Discord constants/types, follow the existing `as const` + `ObjectValues` pattern for consistency.
- If adding timers in future `Client`/`Rest` code, chain `.unref()` immediately to satisfy lint and avoid process hang.
- Add tests under `src/Tests/` or Vitest will not discover them.
- To handle a new gateway dispatch event: create/update a handler in `src/Events/` using `defineEvent(...)`, then export it from `src/Events/index.ts`; `EventDispatcher` auto-registers exported handlers.
- `Rest` targets `https://discord.com/api/v10`; use `client.rest.get<T>(path)` / `.post<T>(path, body)` etc. in cache `fetch()` impls.
- For public API changes, update exports in `src/index.ts` (it already re-exports builders/cache/events/structures/types and core runtime modules).
